# EDL-211 Rust learning note

This work adds the first executable `Run` to Kiln. A Run belongs to one
Session. It starts in `queued`, changes to `running`, and ends in `completed`
or `failed`. A ToolCall belongs to the Run. It starts in `requested`, changes
to `running`, and ends in `completed` or `failed`.

The core owns these state changes. A caller cannot move a completed Run back
to running or complete a ToolCall before it starts. `RunId` and `ToolCallId`
are separate Rust newtypes. Their wire values use the `run_` and `tcl_`
prefixes with canonical ULIDs.

SQLite has one durable row for each Run and ToolCall. A partial unique index
allows only one `queued` or `running` root Run for a Session. The database
therefore keeps this rule correct when two requests arrive at the same time.
The storage adapter also checks the source state, destination state, entity
relationships, and exact Event set before each write. A caller cannot use the
public storage trait to skip the core state machine.

Migration `0003` rebuilds the Event table to add Run and ToolCall columns. It
preserves SQLite's `AUTOINCREMENT` high-water value as well as existing rows.
This prevents reuse of a cursor whose highest Event row was deleted before an
upgrade.

Each accepted state change and its audit Events use one SQLite transaction.
The application receives the committed Events from the store. The daemon then
publishes those Events. It never publishes an Event before the matching rows
commit. One shared sequencer holds each Run commit and its immediate
publication together. Concurrent Runs can execute their subprocesses in
parallel, but their committed Events reach the WebSocket in increasing global
cursor order.

The first executor does not accept a command from a client. It starts the Kiln
executable again with fixed internal arguments. The child writes known stdout
and stderr and exits with success or failure. This is a real process boundary,
but it does not require a model provider, shell, credential, Workspace path,
or permission policy.

Execution uses this order:

1. Commit the queued Run and `run.created`.
2. Commit the running Run, requested ToolCall, and their Events.
3. Commit the running ToolCall and its Event.
4. Start and wait for the subprocess.
5. Commit output, exit status, terminal ToolCall, terminal Run, and Events.
6. Publish each committed Event in cursor order.

The server exposes commands and reads as protocol DTOs. The daemon owns the
background task and executor. The core depends only on a `SubprocessExecutor`
port. The infrastructure crate implements that port and the SQLite storage
traits.

The WebSocket subscribes to the live broadcaster before it reads the current
database cursor. It acknowledges that cursor and ignores any already queued
Event at or before it. This closes the gap where an Event could commit between
the snapshot read and live subscription. Durable reconnect replay still uses
the Session Events HTTP endpoint and belongs to EDL-212.

The persisted Run response includes the ToolCall state, stdout, stderr, and
exit code. A client can read the same terminal result after the daemon starts
again. Public cancellation, process-tree shutdown, approvals, arbitrary
commands, and large-output artifacts remain outside EDL-211. EDL-213 adds the
first public cancellation and graceful daemon shutdown slice.
