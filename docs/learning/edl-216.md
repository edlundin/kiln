# EDL-216 Rust learning note

EDL-216 closes the first vertical slice with one outside-in test. The test uses
only the public HTTP and WebSocket protocol against the real `kilnd` process,
SQLite store, file artifact store, and deterministic subprocess fixture. It
does not call core or adapter internals to prove the result.

## Learning checkpoints

1. **Own process lifetime with RAII.** The `Daemon` fixture owns
   `std::process::Child`. Its `Drop` implementation stops abandoned fixtures,
   while explicit SIGINT and SIGTERM paths prove graceful shutdown.
2. **Keep durable identity across process replacement.** The test retains IDs,
   the credential, and the data-directory path as owned values. A replacement
   daemon can then recover the same Workspace, Session, Runs, event cursor, and
   artifact without borrowing the old process fixture.
3. **Treat a WebSocket cursor as a durable boundary.** The test saves the first
   Run Event cursor, disconnects, restarts, reconnects with `after`, and compares
   the streamed suffix with the HTTP event-history suffix. Strictly increasing
   numeric cursors prove order; value equality proves replay content.
4. **Verify permission before side effects.** An `Ask` Run reaches
   `waiting_for_approval` while its large-output subprocess PID marker is
   absent before and after daemon restart. The deterministic subprocess writes
   that marker after approval, and `approval.decided` precedes the first output
   or artifact Event. These observations prove that permission gates execution.
5. **Measure without making a limit.** `Instant` records reconnect,
   cancellation, and shutdown durations. `ps` samples daemon RSS while the
   WebSocket is active. The test reports values but has no performance
   assertion, because one local sample cannot define an operational budget.

The RSS helper is intentionally in the black-box fixture. It observes the
daemon process by PID and does not add a production metrics dependency. The
streaming sample runs after every received Event. This adds test cost, but it
keeps the measurement tied to the exact replay and live-stream workload under
test.

### Stalled child test diagnosis

The isolated `child_runs_list_replay_and_recover_as_one_session_tree` check reaches the root approval, then receives `approval.decided`, root `tool_call.state_changed` (`ready` and `running`), and root `run.state_changed` (`running`). The two child Runs remain `waiting_for_approval`, so no root terminal event follows. The existing `finish_owned_execution` path waits for all descendants to become terminal before it finishes the parent (`crates/daemon/src/run_service.rs:478` and `crates/daemon/src/run_service.rs:592`). The test expects the root to become `Completed` while those child Runs are still waiting, which conflicts with that existing behavior. The EDL-216 changes touch only the black-box harness and learning evidence; no production run-service code changed. This stall therefore predates the current EDL-216 edits and remains outside this vertical-slice scope; the follow-up repair is tracked in [EDL-287](https://linear.app/edlundin/issue/EDL-287).
