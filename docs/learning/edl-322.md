## 1 October 2026 continuation

pinned TLS transport and real macOS Keychain adapter. The fixture used only
generated test identities and one follower credential; no existing account,
credential or database was accessed. The published revision was an empty shared

phase is `retired` while its separately journaled credential remains active.

**Preparation closed**, explains that approval can retain a credential, and
offers **Retire enrollment / retry cleanup…**. The API, vault lifecycle and
confirmation behavior are unchanged. Historical approval never becomes a claim
that the credential or remote grant is currently active.

## Shared default consumer continuation

A managed deterministic Run rejected valid published defaults, an exact binding
and a connected fixture account with 503 `model_unavailable`. Source inspection
traced this to the daemon registering its deterministic provider through the
legacy tuple-only path. Its model-start policy therefore reported no adapter for
shared selection. Registration now uses the existing explicit Run-scoped adapter
path, retaining durable account/Workspace validation and exact invocation routing.
The deterministic adapter never resolves credentials or contacts a provider.

The existing disposable master was restarted in deterministic-model mode. A
synthetic connected deterministic account and Workspace association were seeded
while the daemon was stopped; its sentinel reference has no vault entry. This
fixture metadata validates the selection consumer, not real account sign-in.
Binding, publication, Run creation and replay used the ordinary authenticated API.

## Follower shared default consumer continuation

The same disposable authority prepared a new managed identity and enrolled a
fresh follower over pinned TLS. The exported public CA fingerprint was checked
before enrollment. Both daemons used deterministic-model mode; the follower's
synthetic connected account metadata and Workspace association were seeded
while it was stopped. Its sentinel credential reference has no vault entry.
All binding, enrollment, snapshot and Run operations used the authenticated
public APIs. No real account sign-in or provider request was performed.

The follower had its own local binding at version 1. The master's restored
binding was version 3; account bindings and credentials were not distributed.
The listener retained-request capacity was two because the authority retained
the original terminal request and this new request. Connection concurrency
remained one; the other bounds were unchanged from the earlier fixture. These
inputs match this exact serial workload and are not production defaults.
