# EDL-341 — account sign-in and recovery

Issue: <https://linear.app/edlundin/issue/EDL-341>

## 1 October 2026 continuation

The existing daemon collapsed terminal sign-in errors to `failed`, losing expiry,
decline and credential-vault failure distinctions before Settings could present
recovery guidance. Protocol `0.47.0` adds an optional, enumerated `failure` category
to login status. The daemon exports only a safe category; the desktop presents
the matching action in an accessible alert. Cleanup-required and cancelled
attempts retain their existing states. Provider text and private references are
not included. This increment builds on `8ebc6c3`; the commit hash is recorded in
the repository history/changelog.

## Prepared live acceptance scenario

Use a fresh isolated daemon data directory and a disposable Git repository,
with the deterministic executor retained. Launch the rebuilt client with that
daemon's address and credential-file path, then create a saved Session. Do not
use an existing user's daemon or account for failure/disconnect experiments.

1. In native Settings, choose **Sign in with browser**, then explicitly open the
   returned sign-in link. The user completes real OAuth on the daemon's host and
   any OS-vault prompt. Record **Check sign-in** reaching Connected, public account
   metadata without credentials, and the saved Session's Events without secrets.
   Do not retain or publish the authorization URL/query.
2. Restart the daemon and reconnect. Refresh accounts and verify the same durable
   connected account. A new attempt is not a substitute for this persistence check.
3. Exercise actual credential refresh through the existing provider boundary and
   record its rotation/reuse result. Check invalid/expired credential recovery
   without reading or printing vault payloads. Provider-side invalidation needs
   the user's participation and must not affect an unrelated account.
4. Confirm **Keep account**, then explicit **Disconnect** on the isolated account.
   Verify local deletion/disabled state and reauthentication using the same ID.
   If deletion fails, verify cleanup remains retryable after restart and prevents
   another credential write.
5. Exercise an unavailable vault in an approved isolated host environment. Verify
   actionable failure and cleanup status without disabling the user's normal
   Keychain or widening permissions. A fixture result alone does not pass this
   live condition.
