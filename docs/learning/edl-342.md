# EDL-342 — direct ChatGPT identity verification checkpoint

Issue: <https://linear.app/edlundin/issue/EDL-342/complete-a-text-only-codex-subscription-run>

## Initial implementation scope — 1 October 2026

This increment adds a pure verifier for an ID token in the official
[Sign in with ChatGPT direct-registration flow](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).
It validates identity after a caller supplies discovery and JWKS documents; it
does not perform registration, OAuth exchange, network access, credential
storage, scope authorization, or model inference. No native request is wired to
this verifier yet.

The direct-registration contract differs from the existing legacy Codex OAuth
flow documented in [EDL-341](edl-341.md). For a first registration, the official
flow starts with `client_id=dynamic_agent_client` and returns an issued client
ID. Later authorization uses that saved issued ID rather than the registration
entrypoint. The requested ChatGPT plan-use scope is
`chatgpt.tokens.use.direct`. The ID token must be verified against OpenAI's
published keys, with the issuer, issued-client audience, expiration and
transaction nonce checked; its validated `sub` identifies the account. This
verifier also requires `iat` to be present and numeric. Expiry uses zero leeway
and rejects tokens expiring at the current integer second. A valid ID token
alone does not authorize plan usage: the granted scopes still need to include
`chatgpt.tokens.use.direct` before inference. Existing EDL-341 legacy OAuth,
refresh and native account evidence does not establish direct-registration
permission or a direct-grant response.

The verifier pins the expected issuer (`https://auth.openai.com`) and JWKS URI
(`https://auth.openai.com/.well-known/jwks.json`) in discovery, accepts only
RS256, and requires a unique matching key ID whose purpose permits signature
verification. It checks the issued client ID as the audience and binds the
nonce to the current transaction. The result carries issuer, client ID and
subject only; it does not retain the ID token. Discovery/JWKS acquisition over
the pinned HTTPS boundary remains the caller's responsibility. Document, token
and identity-field size limits are local allocation safeguards, not provider
requirements.

The fixtures contain a synthetic never-issued RSA signing key and its public
JWKS. They are for local tests only and provide no real account credential or
provider authorization.

Checks on this increment:

```sh
rtk proxy cargo test --locked -p kiln-providers --lib chatgpt_identity::tests -- --nocapture
rtk proxy cargo check -p kiln-providers
rtk proxy rustfmt --edition 2024 --check crates/providers/src/chatgpt_identity.rs
```

The final locked verifier run passed: 3 passed, 0 failed, 0 ignored, 1 filtered,
0.07 s; compile took 0.95 s. The provider crate check passed in 21.32 s, and the
scoped rustfmt check passed. Required typed `iat` presence and rejection when
`exp` equals the current second are covered. The synthetic private fixture bytes
are intentionally not reproduced in this note. Native direct-registration, token
exchange and live inference remain unverified.
